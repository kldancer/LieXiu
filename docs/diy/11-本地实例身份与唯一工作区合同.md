# 本地实例身份与唯一工作区合同

## 1. 文档定位

本文是 LieXiu DIY 本地/自托管模式的实例身份、owner bootstrap 和唯一内部 Workspace 的
唯一实现依据。它约束 Wave 1C.9 的 schema、query、service、HTTP API、Web 首屏和迁移验收，
并为 Wave 1C.10 删除公开注册、邀请、成员管理和 Workspace 切换提供前置事实。

本文不改变 Mission、TaskNode、Run、Artifact 或 Activity 的 `workspace_id` 分区，不授权合并、
重定向或删除任何已有 Workspace 数据。Wave 1C 删除顺序与实时进度分别见 10 和 08 文档。

## 2. 冻结结论

1. 实例只保存一个 canonical owner 与一个 canonical 内部 Workspace 绑定；该绑定是单例事实，
   不是通过删除其他 Workspace 得到的统计假设。
2. 首启是显式、幂等的 bootstrap 请求，不在 server 启动时无条件写库。它不创建 Agent、
   Chat、Mika、onboarding 内容、AgentTask 或 Run；它只将 canonical owner 的 `onboarded_at` 幂等置位，
   以绕过即将在 1C.11 删除的旧 onboarding 向导。
3. bootstrap 凭据是部署侧 secret；只能由部署的 secret store 注入进程环境，不进入 URL、日志、
   公开配置、数据库明文列或长期文档。
4. 浏览器会话在 1C.9 继续复用现有短时 JWT、HttpOnly cookie、SameSite 和与 JWT 绑定的
   CSRF cookie。这是兼容桥，不宣称 logout 可撤销已泄露的 JWT；可撤销长期凭据仍由 PAT 拥有。
5. 旧邮箱验证码、Google OAuth、邀请、成员管理、新 Workspace 创建与切换 API 在 1C.9
   暂作回退桥；它们不参与 bootstrap，并在 1C.10 按闭包统一删除。
6. daemon 继续使用现有 PAT/JWT 兼容注册路径，`mdt_` 数据模型不删除。1C.9 不为未有
   生产签发者的 `mdt_` 路径虚构新生命周期；其 canonical 签发与撤销必须单独冻结后才可启用。

## 3. 持久化事实

新增 `local_instance` 单例关系，最小形状为：

| 字段 | 合同 |
| --- | --- |
| `singleton_key` | 固定布尔值且为主键，保证全库最多一行 |
| `owner_user_id` | canonical owner 的现有 `user.id` |
| `canonical_workspace_id` | canonical 内部 `workspace.id`；刻意不使用通用清理列名，该实例事实不随 Workspace 删除 |
| `bootstrap_version` | 当前 bootstrap 合同版本，从 1 开始 |
| `created_at` / `updated_at` | 数据库时间事实 |

项目继续遵守“应用层维护关系”约束，该表不新增数据库外键。写入前必须证明：

- owner 和 Workspace 均存在；
- `member(user_id, workspace_id)` 存在且 role 为 `owner`；
- 未存在其他 `local_instance` 行；
- 不修改任何已有业务表的 `workspace_id`。

canonical 绑定是内部路由和授权事实；`ListWorkspaces` 中存在几行不能反推或改写它。

## 4. Bootstrap 决策表

bootstrap 在单一数据库事务内获取 transaction-scoped advisory lock，然后按下表决策：

| 现有事实 | 动作 |
| --- | --- |
| 已有 `local_instance` | 验证关联事实仍有效，返回同一 owner/Workspace，不创建任何行 |
| 空库 | 使用规范化的 owner 和 Workspace 参数创建 User、Workspace、owner Member 与 singleton |
| 唯一明确的 owner + Workspace 关系 | 复用该数据，只新建 singleton |
| 多个 Workspace 或多个 owner 候选 | 必须同时指定 owner email 和 Workspace UUID；任一不匹配则冲突失败 |
| 指定的用户不是目标 Workspace owner | 失败；不自动提升 member/admin |
| 只有 User 或只有 Workspace | 失败；不猜测应创建哪一侧 |
| 关联对象已损坏或被删除 | 失败并进入操作员恢复；不自动换绑 |

两个并发 bootstrap 请求必须返回同一绑定，或其中一个在另一个已提交后重读该绑定；
不得向客户端泄漏唯一冲突、部分插入或已消费凭据的中间状态。

## 5. HTTP 与凭据合同

### 5.1 公开端点

```text
GET  /api/bootstrap/status
POST /api/bootstrap
```

`GET /api/bootstrap/status` 只返回：

- `enabled`：服务端是否配置了合法 bootstrap secret；
- `initialized`：singleton 是否存在且关联事实有效；
- `requires_selection`：旧库是否需要显式 owner/Workspace 选择。

它不返回 email、User ID、Workspace ID、slug、候选列表、secret 或凭据强度。

`POST /api/bootstrap` 接受：

- `secret`；
- 初始化所需的 `owner_name`、`owner_email`、`workspace_name`、`workspace_slug`；
- 旧库存在歧义时必需的 `workspace_id`。

secret 必须使用常量时间比较。失败响应不回显 secret，也不指示具体哪一段 secret 错误。
成功响应返回现有 `LoginResponse` 身份与 canonical Workspace，并设置现有 auth/CSRF cookies。

### 5.2 配置

Wave 1C.9 使用一个专用环境变量 `LIEXIU_OWNER_BOOTSTRAP_SECRET`。空值或弱值使 bootstrap endpoint
fail closed；生产环境同时必须显式配置 `JWT_SECRET`。示例文件只放占位说明，不放可用默认值。

bootstrap secret 的轮换不改写 canonical 绑定；新 secret 只影响之后的 bootstrap/login 请求。

### 5.3 会话、CSRF 与长期 token

- bootstrap 成功后签发的 JWT 与邮箱验证码路径使用同一 TTL 和 claims 形状。
- cookie 默认 HttpOnly、SameSite=Strict；生产发布通过 HTTPS 设置 Secure。
- cookie 认证的非安全方法必须通过现有 `X-CSRF-Token` 验证。
- logout 清除当前浏览器 cookie；已导出的 JWT 在 TTL 内不具服务端撤销能力。
- PAT 继续只返回一次原文、仅存 hash、支持过期和撤销；它是 CLI/daemon 的可撤销长期凭据。

## 6. 固定 Workspace 路由

bootstrap 成功后，Web 从响应或幂等 status/login 结果获取 canonical Workspace，直接进入该
Workspace 的 Mission 入口。前端不再把“Workspace 列表的第一项”当成 canonical 事实。

1C.9 只建立固定路由能力和 bootstrap 首屏；旧 Workspace 创建、列表、切换、邀请和成员页的
删除属于 1C.10。在两个单元之间，canonical 路由与旧路由可同时存在作为可回退迁移桥，
但 Mission 新业务入口只展示 canonical Workspace。

## 7. 失败、恢复与边界

| 失败 | 规范行为 |
| --- | --- |
| secret 缺失、过短或不匹配 | 503 或 401，无数据库写入，无凭据日志 |
| 旧库选择歧义 | 409，要求显式 owner email + Workspace UUID |
| 选中非 owner 成员 | 409，不提升权限 |
| 事务中任一插入失败 | 全部回滚，不保留半个 User/Workspace/Member/singleton |
| 已绑定对象损坏 | fail closed，保留原 singleton 供恢复审计，不自动换绑 |
| 旧 Workspace 中存在 Mission/Run | 原地保留，不合并、不删除、不改 `workspace_id` |
| 需要回退 1C.9 | 禁用 bootstrap endpoint，恢复旧 login/onboarding 入口；singleton 可保留且不影响旧读路径 |

## 8. 分层验收

### 8.1 纯逻辑与 repository

- 请求字段规范化与 secret 校验；
- 空库、已绑定、唯一旧库、多 Workspace、多 owner、非 owner 选择决策；
- 重放返回相同 ID，无额外副作用；
- 两个并发请求最终只有一个 User、Workspace、owner Member 和 singleton。

### 8.2 HTTP 与安全

- status 不泄漏身份和凭据；
- 错误 secret 不写库，成功 bootstrap 设置 HttpOnly auth cookie 和 CSRF cookie；
- 缺少/错误 CSRF 的 cookie 写请求被拒绝；
- owner-only Mission Command 成功，跨 Workspace 依旧失败；
- PAT 创建、仅一次原文、撤销和 daemon 的 PAT/JWT 兼容注册不回归。

### 8.3 迁移与前端

- 最新空库可 bootstrap，已有单/多 Workspace 库完成显式绑定或准确 fail closed；
- 执行迁移不改变任何已有 Mission/Run 的 Workspace 分布；
- Web 首屏能初始化或使用 secret 重新登录，成功后固定进入 canonical Workspace；
- 旧注册/工作区管理桥在 1C.9 仍可回退，1C.10 删除时不再需要发明新身份事实。

## 9. 完成标准

Wave 1C.9 只在以下事实同时成立时完成：

1. canonical owner/Workspace 有唯一持久化事实；
2. 空库首启、重复请求和并发请求都不产生第二 owner/Workspace；
3. 已有库只显式绑定，不改写、合并或删除原 Workspace 数据；
4. owner 安全会话、CSRF、PAT、daemon 兼容注册和 Mission workspace scope 经过回归；
5. Web 可从未初始化到 canonical Mission 入口完成一次闭环；
6. 1C.10 的删除边界已不再与 bootstrap 生产写集合重叠。
